# Shopify / Stripe 付款与客户数据关联

本项目的网站由部署者放到自己的云端。关联的后台数据库可以来自已配置的 Lovable 后台，或由部署者管理的 Supabase 后台。本文定义付款和客户同步的目标及验收标准；**不表示当前代码已接通这些服务**。

## 1. 仅两种外部付款接入

| 接入 | 用途 | 客户来源 |
|---|---|---|
| Shopify | 使用已有 Shopify 商店作为付款入口 | Shopify 客户作为主档案，与网站后台建立关联和双向同步 |
| Stripe API | 通过 Stripe 创建付款会话并收款 | 使用网站自己的客户档案；如另有 Shopify 商店，客户同步可独立关联 |

不增加第三种外部付款提供商。代码中现有会员余额和后台记账属于内部业务功能，不是本文新增的付款接入方案。`VITE_PAYMENT_PROVIDER` 当前一次只选择一个提供商，不表示已实现两种付款入口同时展示。

## 2. Shopify 付款目标链路

1. 客户在云端网站选择场地和时段。
2. 网站服务端验证身份、可订时段和价格，创建带到期时间的待付款预订。
3. 服务端使用自己的商店授权创建 Shopify 结账入口，并记录本地订单与 Shopify 付款对象的关联。
4. 客户进入 Shopify 完成付款。
5. Shopify 付款回调进入云端服务端，验签、查关联记录、核对金额和币种后，原子地确认预订。
6. 网站从后台查询确认结果；客户即使付款后关闭页面，也应能再次查询订单。

订单备注和浏览器传来的会员 ID 不能代替服务端关联记录。Webhook 必须验证签名并处理重复投递，参见 [Shopify 回调验证](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries)。

## 3. Shopify 客户与后台数据库双向打通

### 谁是主档案

使用 Shopify 客户方案时，Shopify 是客户基础资料的主要来源；后台数据库保存关联客户记录以及本系统的场地预订、会员权益、账本和权限。双向同步是允许双方发起受控更新，不是把两张表全部互相覆盖。

下面是拟实现的数据规则，尚不是现有数据库中的完整表结构：

| 数据 | 关联或同步规则 |
|---|---|
| 客户身份 | 用商店标识 + Shopify Customer ID 作为外部唯一关联，映射本地 customer ID；不能只按姓名或邮箱认领账号 |
| 登录身份 | 本地 Auth user ID 单独绑定客户记录；验证本人后才绑定，不同步密码或登录 token |
| 姓名、邮箱、电话等必要资料 | Shopify 主档案同步到后台；网站发起的授权修改先写回 Shopify，成功后更新本地镜像 |
| 会员角色、余额、订场与课程 | 由本系统管理；不允许普通 Shopify 客户字段直接提升管理员权限或覆盖余额 |
| 支付关系 | 保存 provider、提供商交易 ID、本地订单 ID；不混用 Shopify 和 Stripe 的标识 |
| 营销同意 | 按实际客户授权和对应 API 单独处理，不因注册、订场或同步而自动订阅 |

手机号、姓名等只在业务需要且已获授权时同步。不要为“数据完整”复制无关地址、备注或整份客户资料。

### Shopify → 后台

1. 商家授权必要客户读取范围；先用测试数据核对受保护客户字段是否获准访问。
2. 首次分页导入所需客户，按商店 + Customer ID 去重，记录同步游标。
3. 接收客户创建、更新等事件；验证签名、商店来源和事件类型。
4. 先保存去重标识和待处理任务，再更新本地客户镜像；失败进入重试队列。
5. 增加定期对账，补回漏掉的事件；旧事件不能覆盖较新的资料。

### 后台 → Shopify

1. 已验证的客户或有权限的员工修改允许同步的字段。
2. 服务端根据已有映射定位 Shopify 客户；新客户在验证、授权和去重后创建对应记录。
3. 通过 GraphQL Admin API 创建或更新客户，检查返回错误，成功后保存映射与同步版本。
4. Shopify 随后产生的回调可确认镜像，但不能触发无限的来回更新。
5. 失败应显示“待同步”或“需处理”，不能在网站上假装两边已保存成功。

Shopify 提供 [customerCreate](https://shopify.dev/docs/api/admin-graphql/latest/mutations/customerCreate) 和 [customerUpdate](https://shopify.dev/docs/api/admin-graphql/latest/mutations/customerUpdate)；写入要求 `write_customers` 权限，访问受保护客户数据还需满足对应要求。上线实现应固定受支持 API 版本并核对权限，不沿用仓库旧支付草稿中的过时 API 版本。

### 同步冲突与删除

- 每条关联记录需要同步版本、来源、最近成功时间、错误状态；写入采用任务队列和幂等处理。
- 相同 Customer ID 的同一次更新只生效一次；本次写回产生的回调不再反向重复发送。
- 两端同时修改同一字段时标记冲突，重新读取 Shopify 主档案后人工或按已定义规则解决，不能无条件“最后收到谁就覆盖谁”。
- 客户删除、解绑、撤销授权和适用的数据删除请求要传播到关联侧，停止后续重建；历史账务保留策略需另行确定，不因客户删除而盲目抹去账本。

客户资料同步不等于 Shopify 与网站共用登录。单点登录需要额外认证接入，不能靠复制邮箱和客户 ID 实现。

## 4. Stripe API 付款目标链路

1. 网站服务端验证预订，计算应付金额并创建本地待付款订单。
2. 服务端调用 Stripe Checkout Sessions API，保存订单与 Session / PaymentIntent 的关联，返回付款地址。
3. 客户在 Stripe 完成付款。
4. Stripe Webhook 到达后台；验证原始请求签名、环境、付款状态、金额、币种和订单关联。
5. 重复或并发事件只确认一次；如果付款尚未最终成功，预订不能被误标为已付款。
6. 对取消、失败、过期及迟到事件执行明确的订单处理，网站读取后台结果。

不能仅凭成功页面跳转认定收款成功，参见 [Stripe 付款确认](https://docs.stripe.com/checkout/fulfillment) 与 [Webhook 文档](https://docs.stripe.com/webhooks)。Stripe 付款本身不会自动同步 Shopify 客户；二者是独立集成。

## 5. 当前仓库实际完成到哪里

| 项目 | 当前状态 |
|---|---|
| 云端静态网站部署 | 有 Vite 构建与托管配置，可部署演示站 |
| 后台数据与权限 | 有 Supabase SQL、Auth 客户端与部分权限测试，仍需目标环境验收 |
| Shopify / Stripe 付款 | 各有 checkout、webhook 草稿；前端和四个服务端入口均安全关闭 |
| 付款配置 | 类型仅 `shopify` / `stripe`，改配置不会解锁付款 |
| Shopify 客户字段 | `profiles.shopify_customer_id` 仅为预留字段，不代表已经建立可靠关联 |
| 客户导入、创建/更新回调、反向写回 | 尚未实现 |
| 同步队列、去重、冲突、对账与删除传播 | 尚未实现 |
| 外部客户与登录账号分离 | 尚待建模；现有 `profiles.id` 依赖 `auth.users`，不能直接导入所有未注册的 Shopify 客户 |

后续需要客户主表、外部身份映射、同步事件收件箱/发件箱及付款关联表等服务端能力。上文描述的是目标设计，不能在云后台填写几个值后宣称已经“互相打通”。

## 6. 两种接入的验收清单

| 场景 | 应看到的结果 |
|---|---|
| Shopify 新建测试客户 | 后台出现一条对应客户映射，无重复账号 |
| 网站修改已授权资料 | Shopify 对应客户更新；回调后两边一致 |
| 两位客户同名或邮箱改变 | 不错误合并、不抢占账号，不泄露他人预订 |
| 同一事件重复、乱序、失败重试 | 不重复创建、不反复回传、不覆盖新资料 |
| 同步失败或两端冲突 | 显示待处理，可追踪和安全重试 |
| 客户删除或解绑 | 按定义传播并停止重新同步，保护必要账务记录 |
| Shopify / Stripe 各完成一次测试付款 | 交易和预订正确关联，只确认一次 |
| 错误签名、错误金额、错误币种 | 拒绝确认并保留脱敏审计线索 |
| 支付失败、客户放弃、占位到期 | 不扣错余额、不永久占场、不错误确认 |
| 客户付款后未回到网站 | 后台仍通过有效回调更新结果 |

只使用虚构客户、测试商店和测试付款验证。客户真实数据留在各部署者自己的受控后台，任何同步载荷、密钥、回调原文及数据导出都不提交到公开仓库。
