## 正式收款前必须处理

**当前已在前端及四个 Edge Function 入口关闭线上支付。** 代码中的旧支付分支保留用于后续修复，但不会执行；没有环境变量解锁方式。以下问题仍须解决，不能把关闭入口当成完成了支付系统修复。

### 1. 支付凭证未与预订安全绑定（高优先级）

`supabase/functions/shopify-webhook/index.ts` 从 Shopify 订单 note 读取会员或订单 ID。note 是业务内容，不能作为授权依据；处理函数也没有将预期金额、币种、支付交易与待付款订单做完整核对。Stripe 确认分支同样缺少金额与原订单绑定验证。

建议建立服务端 payment intent / payment attempt 表，付款创建时写入不可变预期值，回调以服务商交易 ID 查找并原子确认，拒绝不匹配及已取消订单。Shopify / Stripe 交易标识应带服务商命名空间。

### 2. 待支付占位没有完整生命周期（高优先级）

两个 checkout 函数先插入订单和占用，再调用支付平台。创建支付失败或用户放弃后缺少可靠的释放、过期与补偿逻辑；迟到 webhook 可能直接确认已取消订单。

需要事务化占位、到期清理、明确状态转换，以及回调与取消并发测试。

### 3. 服务端预订校验不足（高优先级）

后续覆盖的购物车 / 计价函数缺少完整的开始时间、30 分钟对齐、营业时间、资源上架、发球机依附与团课占用检查。不同入口的校验不统一，两个表之间也缺少共享的占位约束。

前端禁用按钮不能替代服务端验证。应统一所有入口的校验和锁，并测试两人同时订场、团课与散订冲突。

### 4. Stripe 回调验证不完整（高优先级）

当前签名比较未检查时间容差，只处理第一个 v1 签名；`checkout.session.completed` 未确认 `payment_status` 就尝试入账。启用延迟支付方式时尤其需要单独的成功事件处理和状态校验。

### 5. 财务明细与状态语义（中优先级）

Stripe 订单沿用 `channel='shopify'`；两个 checkout 路径的 booking.price 可能是基础单价，未与含高峰及总时长的订单总额一致。先明确支付服务商字段和行金额语义，再用于正式对账。

## 其他边界

- 交付路径是使用者在自己的云端部署网站，数据库与服务端单独配置；不以 Lovable 网站发布为前提。
- Shopify 客户主档案与后台双向同步尚未实现。`profiles.shopify_customer_id` 仅为预留字段；仍缺独立客户模型、验证后的登录绑定、外部身份映射、双向事件与任务、重试去重、冲突和删除传播。现有 `profiles` 依赖 `auth.users`，不能直接作为完整 Shopify 客户导入表。
- 外部付款目标仅 Shopify 与 Stripe API；两个接入的实现和验收边界见 [付款与客户同步说明](PAYMENTS_AND_CUSTOMER_SYNC.zh-CN.md)。
- 生产数据表没有 `venue_id` 隔离；JSON 切换只适用于演示，不是完整多租户。
- 已新增隐私迁移：原始预订限制为本人或员工读取，课程原始排期限制为员工，公开占用 RPC 只返回场地、时间和固定状态。已有安装需实际执行迁移后生效。
- 后台部分写操作未完整检查错误；演示数据多数是静态样例。不可据此判断实际保存成功。
- 非首页的表单、管理表格和长列表仍可继续优化移动端与错误提示。
- 邮件、退款、支付与数据库 RLS 未完成端到端测试，未验证真实平台配置。

## 验证方式

`npm test` 使用 Node test runner、TypeScript 和本地 PGlite，覆盖价格、夏令时、充值权限、直接修改资料的保护、余额扣款和重复入账。测试从 `schema.sql` 提取实际函数；最小测试表不包括 Supabase 全套 RLS 与 GiST 防撞约束。

`npm run build` 执行 TypeScript 检查并构建静态前端。Hallmark 渲染检查用于界面样式和可访问性线索，不能替代业务测试或完整安全审计。
